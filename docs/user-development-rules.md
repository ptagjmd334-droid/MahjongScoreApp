# MahjongScoreApp ユーザー指定・開発運用ルール（正本）

このファイルを **ユーザーが明示した開発ルール・進め方の Source of Truth** として扱う。

会話が長くなった、新しいチャットへ移動した、過去ログを直接確認しづらい、という場合でも、
**新機能追加・バグ修正・テスト提示・作業終了処理の前にこのファイルを確認する。**

既知の失敗例は `docs/known-mistakes-and-prevention.md`、
短い変更前チェックは `docs/pre-change-checklist.md`、
累計開発時間は `docs/development-time.md` を正本とする。

---

# 1. 最優先の進め方

## R001: 決定済み仕様を再質問しない
- 一度決めた仕様は、まず既存ファイル・GitHub・決定ログ・引継ぎ情報を確認する。
- 「前に決めたはず」の内容をユーザーへ聞き直さない。
- 既存仕様と自然に揃えられるものは自動で揃える。
- 質問してよいのは、以下の場合だけ。
  1. 既存仕様と衝突する
  2. 仕様変更が必要
  3. 未決定の新しいトレードオフがある
  4. ファイル/履歴を確認しても必要情報が本当に見つからない

## R002: 新しい機能追加・修正の前に管理ファイルを見る
変更前に最低限、次を確認する。
1. `docs/user-development-rules.md`（このファイル）
2. `docs/pre-change-checklist.md`
3. `docs/known-mistakes-and-prevention.md` の該当項目
4. GitHub main の最新コード
5. 必要なら要件定義・決定ログ・プロジェクト状態・引継ぎメモ

「前回の失敗に該当しないか」を確認してから実装する。

## R003: ミスは一度したら必ず永続記録する
- 新しいミス・回帰が判明したら、`docs/known-mistakes-and-prevention.md` に追記する。
- 必ず **症状 / 根本原因 / 修正 / 再発防止 / 回帰テスト** を残す。
- 次回同じ領域を触る前に該当項目を見返す。
- 「直した」で終わらず、なぜ起きたかを言語化する。

## R004: 原因を言語化してから直す
バグ修正では、実装前または同時に以下を整理する。
- 何が起きているか
- なぜ起きているか
- どのデータ/DOM/ライフサイクル/ルール/キャッシュが原因か
- どこをどう変えるか
- 前にしたミスと同型ではないか

原因が未確定なら、未確定と明記して切り分ける。推測を確定原因として扱わない。

## R005: バグ修正だけで1バージョンを消費しない
ユーザーがバグ・修正を報告した場合は、
**その不具合を直すだけで終わらず、もともと次に実装予定だった機能も同じバージョンで進める。**
- **目的は版数を揃えること自体ではなく、開発・デプロイ・ユーザーのテストを一回にまとめて効率化すること。** 不具合の原因確認と、元から予定していた次機能の実装を同じ作業単位で進め、両方そろった修正版を一度で公開する。
- **「不具合修正版を先に公開→ユーザーにテスト依頼→同じ版数のまま新機能を後から追加→またテスト依頼」はルール違反。** 名前が同じバージョンでも、二度手間になるのでやらない。
- 両方の実装ができてから、一回のデプロイ案内で、一つの対局・同じ手牌をできるだけ使い回す連続テストを全部まとめて示す。ユーザーに許可を求めず、両方の変更を直接GitHubへ反映する。
- 既に先行公開してしまったときは誤りを明記し、未実装の次機能まで実装した上で、追加の細切れテストを要求せず、最終的な一括テスト一回だけを案内する。

例外:
- 緊急のインフラ/公開障害で、次機能を同時に入れると原因切り分け不能になる場合は、まず復旧を優先してよい。
- その場合も理由を明記し、次の予定機能を忘れない。

# 2. コード変更・GitHub

## R006: 最新コードはGitHub mainを正本とする
- 古いZIP・古い添付・過去チャットのコードを最新版扱いしない。
- 変更前にGitHub mainの対象箇所を取得して確認する。
- 公開版はGitHub Pagesを基準に実機確認する。

## R007: 可能な限りGitHubへ直接更新する
現在の優先運用:
- ZIPをダウンロード
- 解凍
- 全選択
- GitHubへドラッグ
という手作業をユーザーへやらせない。
**GitHub連携で直接編集・コミットを優先する。**

## R008: 全消し→全コピペをしない
- 小さな安全な追記だけで済むなら追記。
- 既存コードの削除・置換・関数内部変更が必要なら、最新ファイルを取得し、必要箇所だけ直接編集する。
- 巨大な `script.js` 全文をユーザーに貼り直させない。
- ユーザーに対象関数を探させない。

### 旧ルールとの関係
以前は「既存削除/置換が必要なら最新ZIPを編集して返す」運用だったが、
現在はGitHub直接編集が可能なので **直接編集を優先**。
ZIPは直接編集できない場合のフォールバックに限る。

## R009: 変更前後に対象範囲を確認する
- 巨大ファイル全部を眺めるのではなく、対象関数・関連DOM・読込順を検索して確認する。
- 可能なら構文チェックを行う。
- 変更した箇所だけでなく、その機能が依存する前後ステップへの影響も確認する。

## R010: 旧パッチを外す時は責務を洗い出す
古い `m8-v*.js` を読込対象から外す場合、
そのファイルが担っていた
- レイアウト
- クリック処理
- state保持
- badge
- portal
- camera stop
などを確認し、必要な責務を移植してから外す。

# 3. 説明・会話の進め方

## R011: 初心者前提で説明する
ユーザーは実装を学びながら進める。
必要な場面では、
- 何をしているか
- なぜ必要か
- コードが何を意味するか
を初心者向けに説明する。

ただし単純な「次のテスト」では長すぎる説明を挟まず、具体的操作を優先する。

## R012: マイルストーン区切りで進める
大きな作業は段階に分け、
- 今どこか
- 何が終わったか
- 次に何をするか
が分かるようにする。

## R013: 「はい次」「次」では質問せず次へ進む
- 「何をしますか？」と返さない。
- 既存ロードマップと現在地点から、こちらで次の具体的作業を選ぶ。
- 決定済み仕様をもう一度確認しない。

## R014: スクショは必要な時だけ
- 普通に進められる場面ではスクショを求めない。
- 画面差異、エラー、配置、実機固有挙動など、視覚確認が必要な時だけ依頼する。
- 「スクショください」を各ステップの習慣にしない。

## R015: 外部サービス設定は数手まとめて案内
Supabase/GitHub Pages等の設定は、
**3〜5手順程度をまとめて**
- 何を押す
- どうなる
- 何が見えたら成功
まで具体的に案内する。
画面が想定と違う時だけスクショで切り分ける。

# 4. テストの出し方

## R016: テストは全部まとめて一気に出す
テスト項目を1つずつ小出しにしない。
可能な範囲で、**その機能群のテストを1セットとしてまとめて提示する。**

## R017: 連続してテストできる設計にする
- 同じ対局
- 同じ手牌
- 同じ入力状態
をできるだけ保持し、
条件だけ切り替えて連続テストできるようにする。

毎回、
- 14枚を作り直す
- 名前/親を設定し直す
- 対局を最初からやり直す
というテスト手順を避ける。

## R018: テスト指示は具体的な操作を書く
「確認してください」だけでなく、
**どのボタンをどの順番で押すか**まで書く。

例:
`アガリ → ロン → 和了者 → 放銃者 → 点数表 → 戻る → 戻る → キャンセル`

## R019: 最後にまとめて結果報告できる形にする
ユーザーは、
- 「①〜⑩全部OK」
- 「③だけダメ」
のようにまとめて返せるテスト形式を優先する。

## R020: 前に直した箇所も該当カテゴリなら回帰テストする
新機能が
- 点数表
- アガリフロー
- カメラ
- PWA復旧
- 保存
などに触れた場合、そのカテゴリの既知バグをまとめて再確認する。

# 5. iPhone / PWA / デプロイ

## R021: 実機の主対象はiPhone PWA
- 日常テストの主対象はiPhoneのホーム画面版。
- PCだけで「直った」と判定しない。
- routineなデプロイ/テストのためにMac操作を毎回要求しない。

## R022: 毎デプロイで版数を見えるようにする
- 左下のbuild badgeを更新。
- `?v=...` のcache-bustも更新。
- index.htmlが新ファイルを実際に読み込んでいることを確認する。

## R023: デプロイは公開状態まで確認する
変更したと主張する前に可能な範囲で、
- commit成功
- index反映
- GitHub Pages workflow
- head SHA
を確認する。

ユーザーに数分おきの手動リロードを何度もさせない。

## R024: 更新問題を一括りにしない
以下は別問題として切り分ける。
- GitHub commit
- Pages build/deploy
- CDN/HTTP反映
- Safariキャッシュ
- PWA/Service Worker
- アプリ内update検知

# 6. 保存・仕様管理

## R025: 決定事項はファイルに残す
長いチャットで前方ログが読めなくなることを前提に、
重要な
- 仕様
- 開発ルール
- 既知ミス
- 開発時間
- 作業終了時点
を会話だけに置かない。

## R026: 新チャット/引継ぎ時は管理情報を先に確認
管理ファイルが利用可能な場合、優先して確認する。
- 完全引継ぎ文
- 開発者向け要件定義書
- 決定ログ
- プロジェクト状態
- 引継ぎメモ
- 最新コード

現在コードの正本はGitHub main。

## R027: 保存系は「確定対局」と「入力途中」を分ける
既存決定:
- 確定済み対局状態は通常保存
- 入力途中は別保存
- 復旧時は「続きから再開 / 破棄」を選べる

この分離を新機能で壊さない。

# 7. 作業終了・開発時間

## R028: 「今日はここまで / 終わり / 終了」で自動的に終了処理
ユーザーが作業終了を示したら、確認を挟まず、
その日の作業記録を保存する。

最低限記録する:
- 日付
- 完了内容
- 未完了内容
- 現在地点
- 次回の開始地点

「記録しますか？」とは聞かない。

## R029: 申告された作業時間を累計へ加算
ユーザーが
「今日は6時間」
「2時間やりました」
等と明示した時だけ加算する。
推測時間は加算しない。

累計は `docs/development-time.md` の値を唯一の正本とし、
過去チャットから再計算しない。

## R030: 現在の累計は23時間30分を基準
2026-09-17時点でユーザーが確認した累計:
**23時間30分**

今後はこの値へ、ユーザーが明示した新しい作業時間だけを加算する。

# 8. 現在の固定プロジェクト方針

## R031: スマホ横画面を基本UIとする
麻雀対局管理アプリはスマホ横画面で使うことを前提にUIを整える。

## R032: 実用と就活ポートフォリオの両方を意識
ただ動くデモではなく、
- 実際の対局で使える
- 友人に試してもらえる
- 面接で説明できる
ことを意識して進める。

## R033: カメラ最終目標
最終的なカメラ入力は、
**実牌をカメラで見せる → 13/14枚を認識・カウント → 安定したら自動で次へ**
を目標とする。

現段階では手動補正や論理14枚入力を併用してもよいが、
最終目標を忘れない。

# 9. 優先順位が衝突した時

1. ユーザーが直近で明示した指示
2. この `user-development-rules.md`
3. 決定済み仕様/要件定義/決定ログ
4. `known-mistakes-and-prevention.md`
5. 実装上の都合

古いルールと新しいルールが衝突した場合は、新しい明示ルールを優先し、
このファイルも更新する。

# 10. 新しいユーザールール追加フォーマット

ユーザーが新しい開発ルールを明示したら、会話だけに残さず追記する。

```
## R0XX: ルール名
**ユーザー意図:**  
**実行ルール:**  
**例外:**  
**確認方法:**  
```


## R034: 実機結果から次の開発指示を内部で作り、そのまま実行する
**ユーザー意図:** 実機テスト結果やスクリーンショットのたびに、こちらが作った開発指示文をユーザー自身がコピーして再送する二度手間をなくす。  
**実行ルール:** ユーザーが実機結果・スクリーンショット・「次」「それして」等を送ったら、既存ルール・決定済み仕様・現在地点を確認し、必要な次バージョンの作業指示を内部で整理して、そのままGitHub修正・テスト・公開確認まで進める。ユーザーへ「この文をコピペしてください」と要求しない。  
**例外:** 既存仕様と衝突する、仕様変更が必要、未決定の新しいトレードオフがある、または権限/外部操作上ユーザー本人の操作が不可欠な場合のみ確認する。  
**確認方法:** 通常の実機フィードバック後、ユーザーの再コピペなしで次の修正作業が開始されていること。  


## R035: 手牌入力pickerは三色を縦に揃え、字牌は右側へまとめる
**ユーザー意図:** 手牌修正時に同じ数字の萬子・筒子・索子を視線移動少なく選べるようにする。  
**実行ルール:** 12列×3行の牌一覧では、1〜9萬の位置は現状の左9列1段目から動かさない。その真下2段目に1〜9筒、3段目に1〜9索を同じ列位置で並べる。字牌は右側3列へまとめ、全34牌・Top3・撮影プレビュー・閉じるボタンをiPhone横画面1画面内に維持する。  
**確認方法:** 1段目左9列=1〜9萬、2段目左9列=1〜9筒、3段目左9列=1〜9索。右側に東南西/北白發/中がまとまっていること。
