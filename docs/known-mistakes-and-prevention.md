# MahjongScoreApp 既知ミス・再発防止ログ（正本）

このファイルを **MahjongScoreApp の既知ミス・再発防止の Source of Truth** として扱う。

## 運用ルール
- 新機能追加・バグ修正の前に、まずこのファイルを確認する。
- 変更内容が下記のどの項目に触れるかを確認し、該当する再発防止チェックを先に行う。
- バグが新しく見つかったら、**症状 / 根本原因 / 修正 / 再発防止 / 回帰テスト** をこのファイルへ追記してから、または修正と同じコミット群で更新する。
- 「直ったように見える」だけで完了扱いにしない。iPhone実機/PWAで確認する。
- 原因が未確定なものは「未確定」と明記し、推測を確定事項として残さない。
- 古いパッチを外す時は、そのパッチが担っていた別機能まで消えないかを確認する。
- 版数表示だけでなく、**index.htmlの読込対象 / 実ファイル / GitHub PagesのデプロイSHA** を確認する。
- このログが長くなっても、日常作業では別ファイル `docs/pre-change-checklist.md` の短いチェックを先に使い、必要な項目だけ本ログへ戻る。

# A. 開発手順・コード構造

## M001: 追記パッチ累積で同名関数・処理が競合し、全ボタン無反応
**時期:** 2026-09-12頃  
**症状:** 追加パッチ後、設定画面は出るがボタンが反応しない。  
**原因:** script.js末尾へ修正を積み重ね、同名関数の再定義・上書きやJS停止が発生しやすい構造になった。  
**修正/教訓:** 関連箇所だけを確認しつつ、変更後は全体構文チェック。数機能ごとに整理する。  
**再発防止:** 
- 同名関数を「とりあえず後ろで再定義」しない。
- 既存処理を差し替えるなら、どの旧処理を無効化するか明記。
- 新パッチを増やす時は、既存パッチとの責務重複を確認。
**回帰テスト:** 対局開始、アガリ、流局、リーチ、Undo、メニューの主要ボタンを一周。

## M002: 現在の実ファイルを確認せず推測で修正し、既存仕様を壊す
**症状:** 修正自体は正しそうでも、既存DOM/関数/読込順と合わず別の不具合が出る。  
**原因:** 直前の実ファイルではなく、過去の想定や会話上の状態を基準に変更した。  
**再発防止:** 変更前に必ず対象ファイルの関連箇所を取得する。必要なら index.html の読込順も確認。  
**回帰テスト:** 変更対象だけでなく、その前後1ステップも操作。

## M003: 古いパッチを外した時に、そのパッチが担っていた別機能まで消えた
**例:** v10を外した結果、body直下へのoverlay移動やプレイヤー選択補助まで失われ、v18のCSS前提が崩れた。  
**原因:** 1つのパッチが複数責務を持っていたのに、不要機能だけを消したつもりでファイル全体を外した。  
**再発防止:** 古いファイルを読込対象から外す前に「そのファイルが担う機能一覧」を確認し、必要機能を先に移植する。  
**回帰テスト:** 旧パッチが触っていたUI/操作をすべて再確認。

## M004: バージョン別パッチを積みすぎて競合し、原因特定が難しくなった
**症状:** v8/v18/v21等が同じ点数表や符表示を別々に装飾し、古い表示やクラスが残る。  
**原因:** バージョンごとの応急パッチを長期間同時読込した。  
**再発防止:** 
- 同一領域を3世代以上のパッチが触り始めたら整理候補。
- 新版で責務を一本化したら古い版は読込から外す。
- ただしM003の確認を先に行う。
**回帰テスト:** DOMに旧版ID/クラス/表示が残っていないか確認。

# B. バージョン・デプロイ・キャッシュ

## M005: 「ファイルは作った」だけで公開版に読み込まれていなかった
**例:** m8-v10.jsは存在したが、当時の index.html が v9表示のままで m8-v10.js を読んでいなかった。  
**原因:** ファイル作成と index.html 更新を別々に扱い、公開入口を確認していなかった。  
**再発防止:** 新バージョンでは必ず  
1. 新ファイル存在  
2. index.html読込  
3. バッジ  
4. cache-bust query  
5. Pages最新SHA  
をセットで確認する。

## M006: 古いスクリプトが新版バッジを後から上書き
**例:** 古いM8スクリプトが実行後にバッジを書き換え、実装と表示版数がズレた。  
**原因:** 複数パッチが `#app-build-badge` を書き換えていた。  
**再発防止:** バッジ更新は原則最新パッチ1箇所だけ。旧版のbadge書換えは無効化する。

## M007: v20の補助スクリプトが非同期で読み込まれ、v21表示をv20へ戻した
**症状:** v21を公開したのに左下がv20。  
**原因:** m8-v20.jsが後から m8-v20-stable.js を読み込み、バッジ/挙動を上書き。  
**再発防止:** 動的script挿入があるファイルを新バージョンで残さない。index.html以外からのバージョンスクリプト読込を検索する。

## M008: GitHub Pagesは成功しているのにiPhoneで旧版が見え続けた
**時期:** v11反映時。  
**症状:** Pages workflowはv11成功なのにSafari/PWAはv10。  
**確認事項:** 当時の sw.js は古い `mahjong-score-app-m7-v3` キャッシュ名で、`./` と `index.html` をキャッシュしていた。ただしこれ単独が根本原因だったとは確定していない。  
**再発防止:** 
- 更新問題では「GitHub上のindex」「Pages workflow」「Safari直URL」「PWA」の4層を分けて調べる。
- キャッシュ原因と断定する前にunique query/unique fileで切り分ける。
- sw.jsの古いキャッシュ名・shellキャッシュを放置しない。
**回帰テスト:** Safari直URLとホーム画面PWAの両方でバージョン一致。

## M009: Netlify無料枠/クレジットでデプロイが止まり、検証環境が混線
**症状:** Netlifyが新規デプロイできず、GitHub Pagesへ移行。  
**教訓:** 公開元が変わるとキャッシュ・URL・PWA挙動も変わる。  
**再発防止:** 実機テストの公開元はGitHub Pagesを正本として固定し、別ホストの結果を混ぜない。

## M010: デプロイ通知をアプリ更新問題の解決と混同
**症状:** 「更新されたら通知」の話と、実際のPWA更新反映問題が混ざった。  
**教訓:** 通知機能は反映速度を改善しない。  
**再発防止:** デプロイ完了通知、CDN反映、ブラウザ/PWAキャッシュ、アプリ内update検知を別問題として扱う。

# C. iPhone/PWAレイアウト・中央配置・スクロール

## M011: fixed要素がtransform祖先の影響を受け、アガリ画面が真ん中に来ない
**症状:** アガリ方法/和了者選択が上・左へズレる。  
**原因:** `#agari-overlay` が transformed ancestor 内にあり、fixedの基準がviewportにならなかった。  
**修正:** overlayをbody直下へ移す方式。  
**再発防止:** fixedモーダルはbody直下を基本にし、親transform有無を確認。

## M012: vw/dvhや物理画面サイズを基準に中央計算し、iPhone PWAでズレた
**症状:** 左半分、左下、右/下見切れ。  
**原因:** Safari/PWAの実表示領域と `vw/dvh` / 物理画面サイズが一致しないケース。  
**修正:** 実際に表示されている `#game-screen.getBoundingClientRect()` / visualViewportを基準にする。  
**再発防止:** 「中央」はCSS感覚ではなく、表示後にrectを実測して中心差を検証。

## M013: PWA復帰後にviewportが壊れ、下部空白・見切れ
**症状:** バックグラウンド復帰後、下に空白や右/下の見切れ。タスクキルで直ることがあった。  
**原因:** 復帰ライフサイクルでviewport再計算が不安定。  
**再発防止:** pageshow / visibilitychange / orientationchange後に実表示領域を再測定。ただし無制限な多重タイマーは避ける。

## M014: 点数表を小さくしすぎた
**例:** v17で `scale(.76)` を残し、中央には来たが表が小さい。  
**原因:** 「見切れ対策」を縮小だけで解決しようとした。  
**再発防止:** まず本文スクロール＋固定フッター。縮小は最後の手段で、実機で可読性確認。

## M015: 点数表の下ボタンをstickyにしたが、DOM上は途中にあり上へ浮いた
**症状:** 「戻る / 点数を直接入力 / 次へ」が表の途中に表示。  
**原因:** stickyは「DOM上の位置」を変えない。表の下に別要素がある状態で途中のactionsをsticky化した。  
**修正:** actionsをスクロール領域の外へ物理的に移し、実フッター化。  
**再発防止:** 固定したい操作はDOM構造も「header / scroll body / footer」にする。

## M016: 点数表フッターを別画面でも残し、ロン/ツモ画面にボタンが出た
**時期:** v13→v14。  
**症状:** 「戻る / 点数を直接入力 / 次へ」がロン/ツモ選択時にも表示。  
**原因:** score画面でreparentしたfooterを非score画面でcleanupしていなかった。  
**再発防止:** 画面モード切替時にscore専用DOM/classesを必ずcleanup。

## M017: CSSが `body > #agari-overlay` 前提なのにoverlayがgame-screen内に残り、スクロールが効かなかった
**症状:** 表下部が押せず、縦スクロールも不可。  
**原因:** v10を外したことでportal処理が消えたが、v18 CSSはbody直下前提のまま。  
**修正:** v19でbody直下へportalし、3段構造へ。  
**再発防止:** CSSセレクタ前提と実DOM階層をDevTools/コードで一致確認。

## M018: 放銃者/和了者選択画面まで点数表と同じ大きな幅
**症状:** 横に長く押しづらい。  
**原因:** non-score画面を一律サイズ化。  
**修正:** stepごとにwidthを分離。  
**再発防止:** score / winner / discarder / type は別レイアウト種別として扱う。

## M019: 下側プレイヤーが選択できない/overlayがタップを奪う
**症状:** winner/discarder選択で下プレイヤーが押せないケース。  
**原因:** overlay/pointer-events/riichi領域との競合。  
**修正:** capture phaseでplayer-panel clickをルーティング。  
**再発防止:** 4方向すべてを毎回テストし、リーチ領域を押した場合も確認。

## M020: 起家マークが和了/放銃マークと重なった
**症状:** 状態マークと「起」が重なる。  
**原因:** 同じアンカー/座標系に複数バッジを配置。  
**修正:** 起家マークを起家本人から見て右下へ独立配置。  
**再発防止:** 恒常マーク（起家）と一時状態マーク（和了/放銃）を別レイヤー・別アンカーにする。

## M021: カメラ追加後、メニュー最下部「閉じる」が見切れた
**原因:** メニュー項目増加に高さ設計が追従しなかった。  
**再発防止:** メニュー項目追加時は最小端末サイズで最下部操作まで確認。

# D. カメラ・MediaStream・負荷

## M022: 手牌確認後もカメラMediaStreamが生き残り、iPhoneがカメラ使用中になった
**症状:** iPhone上部が緑、スクショでシャッター音、ボタン反応が遅い、タスク切替時に一瞬カメラ画面が見える。  
**原因:** カメラのキャンセル経路ではstopしていたが、手牌確認→役判定へ進む経路でMediaStream tracksを確実にstopしていなかった。  
**修正:** 手牌確定/画面遷移/pagehide/visibility hiddenで全track.stop。  
**再発防止:** カメラ画面から出る全経路にstopMediaを置く。  
**回帰テスト:** カメラ終了後にiOS緑インジケータが消えること。

## M023: DOM監視が自分の更新を再検知し続け、v15で強いラグ
**症状:** ボタン反応遅延、画面が重い。  
**原因:** MutationObserverがclass/DOM変更を監視し、そのcallback自身がclass/DOMを書き換えて再発火。  
**再発防止:** observerは必要なmutationだけに限定。自分が書き換えるclass/characterDataを監視しない。可能ならユーザー操作イベントで明示更新。

## M024: 点数表の監視ループで白画面→PWA再起動風→途中入力復旧
**時期:** v23→v24。  
**症状:** 点数表に青/橙/緑が出た直後、しばらくすると白くなり「入力途中データがあります」で戻される。  
**原因:** 明示的な `location.reload()` は無かった。v8/v18のobserverが、自分で追加する推奨装飾/ボタンを再検知し続ける構造だったため、iPhone WebViewの負荷上昇要因になっていた。WebView再起動そのものの内部理由はOS側で完全には確定不能だが、自己再発火ループはコード上で確認済み。  
**修正:** v8はchildList/data-tileだけ、v18は点数表DOM新規追加だけを監視。推奨ボタンは毎回作り直さず再利用。  
**再発防止:** MutationObserver追加時は「callbackが自分の監視対象を変更していないか」を必ずレビュー。  
**回帰テスト:** 点数表を30秒以上放置し、白画面/再起動/CPU負荷が出ない。

# E. 手牌入力・カメラ結果

## M025: 連続牌選択で毎回1番スロットを上書き
**時期:** M8 v3初期。  
**症状:** 複数牌を選んでもslot1だけ変わる。  
**原因:** picker/title更新を契機にcurrent indexがリセット。  
**修正:** picker clickをcaptureし、pickerを開いたままcurrent slotだけ進める。  
**再発防止:** 連続入力UIでは表示更新と選択状態の初期化を分離。

## M026: 「読み取り直す」がライブカメラではなくゲーム画面へ戻る
**原因:** 戻り先を一般的なclose処理に任せた。  
**修正:** hand-resultの戻る操作をライブカメラ起動へ明示ルーティング。  
**再発防止:** 「戻る」の意味を各画面で仕様化し、単純な前画面復帰と混同しない。

# F. 符計算・面子・状態受け渡し

## M027: 通常形で符が出ず、七対子だけ25符・国士だけ「符なし」
**症状:** 通常アガリでは青の翻は出るが緑推奨が無い。  
**原因:** m8-v8は複数の符候補があると `m8SuggestedFuV8=null` にする仕様で、点数表側が単一推奨を作れなかった。  
**教訓:** 「計算できない」のではなく「複数候補」の場合をUIで解消する必要がある。  
**再発防止:** nullの意味を「失敗」と「複数候補」で分ける。候補選択UIか、追加情報取得で一意化。

## M028: v13で符表示を直したつもりでも、結果画面に符が出なかった
**原因:** 待ち候補までは取れていたが、実際の和了者/ロンツモ等の状態と符計算の接続が不完全。  
**再発防止:** 符計算の入力値（14枚、和了牌、門前/副露、ロン/ツモ、和了者、面子状態）を一覧化し、どの画面で確定するかを確認してから実装。

## M029: 「14枚あるのに0枚」
**時期:** v18。  
**症状:** 画面には14枚表示されるのに「手牌が14枚ではありません（0枚）」。  
**原因:** 表示DOMの14枚と符計算の参照元 `window.m8LastTilesV8` が別で、参照側が空。  
**修正:** v19で結果画面DOMから実際の14枚を読み、状態へ同期。  
**再発防止:** 同じ情報のSource of Truthを増やしすぎない。画面と計算が別データ源を使う場合は同期点を明示。

## M030: 旧符候補表示が残り、新しい確定符と矛盾して見えた
**例:** 上で50符確定なのに下に「50・60符候補」。  
**原因:** v20の新計算とv18の旧表示が同時に生きていた。  
**再発防止:** 新しい計算系を有効にする時、旧表示DOMをhide/removeし、ユーザーに複数の真実を見せない。

## M031: 副露ありだけでは正確な符が一意に決まらない
**原因:** 「副露あり」だけでは、どの刻子を鳴いたか、明刻/暗刻、明槓/暗槓が分からない。  
**修正:** チーのみ / ポン / 明カン / 暗カンを面子単位で指定。  
**再発防止:** ルール上必要な情報を「推測」で埋めない。足りない情報はUIで取得。

## M032: カンを物理4枚のまま14枚入力に入れようとすると牌数モデルが破綻
**教訓:** 論理手牌14枚では刻子3枚として扱い、別途「明カン/暗カン」を指定して符を加算する設計が必要。  
**再発防止:** 実牌枚数と和了形判定用の論理牌数を分離。

## M033: 符計算の原因を説明せず位置/表示だけ直し続け、修正が往復
**症状:** v13〜v18で「符が出ない」「中央にならない」修正が何度も往復。  
**原因:** その場の見た目修正を先にし、入力状態・DOM階層・計算データフローの根本原因を十分言語化しなかった。  
**再発防止:** ユーザー要望通り、修正前に必ず「症状→原因→どこを直すか」を言語化する。

# G. 役・翻・点数表連携

## M034: 役/符の新旧表示が同居してユーザー判断を迷わせる
**原因:** v5/v18/v20/v21等が別々に説明・候補表示を追加。  
**再発防止:** 同じ概念は最終的に1つの表示へ集約。新判定が確定したら旧候補を消す。

## M035: 点数表の青列・橙符行・緑推奨セルは「計算結果」ではなく一時DOM装飾だった
**症状:** 初回は出るが、ページ再起動/入力途中復旧後は消える。  
**原因:** core draftは `agariFlow`（step, winners, discarder, scoreResults等）しか保存せず、M8の14枚・和了牌・門前/副露・ポン/カン内訳・符・翻を保存していなかった。  
**修正:** v24でM8補助状態をlocalStorageへ保存し、途中入力復旧時に再注入して青/橙/緑を再装飾。  
**再発防止:** 「画面に見えている重要状態」がDOMだけに存在していないか確認。復旧対象は計算元データまで保存。  
**回帰テスト:** 点数表表示→再起動/復旧→青/橙/緑が同じ状態で戻る。

# H. PWA/保存・復旧

## M036: 対局本体の自動保存と入力途中保存が別系統で、M8状態が抜けた
**構造:** 
- 対局本体: `MahjongScoreApp_local_match_v1`
- 入力途中: `MahjongScoreApp_draft_v1`
- M8判定: 当初はwindow変数/DOM中心
**原因:** 後からM8を追加したため、保存設計に組み込まれていなかった。  
**再発防止:** 新しい状態変数を追加した時は「通常保存 / 入力途中復旧 / クラウド同期 / Undo」の4箇所に必要かを確認。

## M037: 開発時間の累計を会話上の部分記録から再計算し、12時間50分と誤答
**正しい値:** ユーザー確認済み累計は **23時間30分**。  
**原因:** 不完全な個別記録を足してしまった。  
**修正:** `docs/development-time.md` を唯一の正本にした。  
**再発防止:** 開発時間を答える/更新する前に必ず同ファイルを読む。過去セッションを再加算しない。

**再発防止:** 画像認識条件は合成画像だけで決めず、実際の撮影スケールを基準にする。ライブ候補数をUX上の必須ゲートにしない。位置検出用の低解像度画像と牌種確認用の高解像度画像を分け、撮影範囲と元動画座標の変換を自動テストする。
**回帰テスト:** Chromium横画面で固定白枠のシャッターボタンとキャンセルの非重複、`object-fit: cover` の元動画座標変換、密着した長い白色牌列の検出、14分割、14個の高解像度プレビュー生成を確認。iPhone PWAでは実牌14枚を一度だけ並べ、撮影→14プレビュー→誤り修正→読み取り直し→カメラ緑表示消灯を一括確認する。
**確度:** 個別牌高さフィルタと実機表示スケールの不整合はコード＋実機スクリーンショットから確認。密着牌の連結成分化も設計上の有力要因。各実フレームの内部ログによる寄与率は未確認。

## M054: 14分割には成功したが確認画面が細い縦切り表示になり、初回学習も保存前に画面が閉じていた
**時期:** M7 v36
**症状:** iPhone実機で白枠内の牌列は14枚に分割できたが、確認画面では各牌が細長い縦ストリップのように見え、`0 / 14枚を自動候補化` のままだった。
**根本原因:** 実写プレビューを縦長の14列ボタンへ `background-size: cover` で表示していたため、各牌画像の中央部分だけが拡大表示されていた。さらに学習保存のdocument click listenerが通常のbubble phaseで動いており、`この手牌で進む` の既存 `onclick` が結果overlayを先に閉じた後ではDOMから14ラベルを読めない経路があった。
**修正:** 実写プレビューを `background-size: contain` と有限高さへ変更し、牌全体を表示。学習保存listenerをcapture phaseへ移し、結果画面が閉じる前に14枚の検証済みラベルと特徴量をlocalStorageへ保存する。学習データが空の初回は「初回学習」と明示し、今回は14枚を手動指定すれば次回候補に使われることを案内する。公開asset queryとPWA cacheも更新。
**再発防止:** 画像の切り出し成功とUI表示成功を別テストにする。ユーザー確認後の学習・保存処理は、画面を閉じるhandlerとのイベント順序を自動テストする。初回学習データ0件を「認識失敗」と誤解させない。
**回帰テスト:** Chromium横画面で撮影→14実写プレビュー→computed styleのbackground-sizeがcontain→14ラベル付与→確定クリック→overlayが閉じても14種類の学習テンプレートがlocalStorageに残ることを確認。その後通常の対局開始〜採点画面フローも通す。
**確度:** プレビュー表示原因・学習イベント順序ともコードと実機表示から確定。自動テストで修正済み。iPhoneでの学習後の次回自動候補精度は実機確認待ち。

## M055: 2回学習後の3回目撮影で自動候補が6/14から0/14へ落ちた
**時期:** M7 v36
**症状:** 初回14枚を手動確定→2回目は6/14を自動候補化→残りを修正して再学習した後、3回目の同じ手牌撮影で0/14へ低下した。14分割自体は継続して成功。
**根本原因:** 学習テンプレート消失ではなく、現在の96要素（8×12）グレースケール特徴が、撮影ごとの牌位置・切り出し位置の小さなズレに敏感だった。テンプレート追加は同一ラベル内の最小距離を悪化させないため、6→0の低下は撮影3回目の特徴が既存テンプレートから閾値外へずれたことを示す。実機の各距離値は今回未取得だが、コード上の特徴表現は位置ずれ不変ではない。
**修正:** 96要素特徴同士の比較時だけ、8×12格子を上下左右±1セルずらした複数比較の最小RMS距離を採用する。ずらしには小さなペナルティを入れ、既存の判定閾値0.24・競合ラベルmargin 0.035は維持して誤認識を増やしすぎない。既存の端末内学習データ形式は変更しないため、再学習のやり直しは不要。各牌の上位3候補距離も診断情報へ保存する。
**再発防止:** テンプレート画像比較では、明るさ正規化だけでなく小さな平行移動に対するロバスト性を単体テストする。認識率が上下したときに同じ手牌の再学習だけをユーザーへ繰り返し求めず、特徴距離と切り出しずれを先に確認する。
**回帰テスト:** 8×12の特徴を1セル横へずらした合成データで、通常RMSは閾値超え、shift-tolerant RMSは正解ラベルを近距離として選べることを確認。全既存役・符・カメラ・Chromium横画面テストも成功。
**確度:** 特徴表現が位置ずれに弱いことはコード上で確定。今回の実機0/14への寄与は有力。修正後のiPhone認識率は実機確認待ち。

## M056: v37のシーム補正で分割境界がむしろ不安定になり、自動候補が0/14へ低下した
**時期:** M7 v37→v38
**症状:** 同じ14枚の比較で、旧v36画面は1/14、最新v37画面は0/14。v37では複数の切り出し画像に隣接牌や木目が入り、末尾側でも牌面が枠から外れる箇所が見えた。
**根本原因:** v37で追加した「縦エッジ＋白牌面の少なさ」によるシーム探索が、牌間境界だけでなく牌模様そのものの強い縦線も拾い得た。実機では内部境界を誤って移動させ、均等分割より不安定なcropを作る回帰になった。
**修正:** v38ではシーム補正を認識経路から外し、実機で相対的に安定していた牌列全体の14等分へ戻す。代わりに分類側を変更し、牌面正規化後の画像から12×18の「インク量」特徴（背景輝度に対する暗さ＋色差）を生成して照明差の影響を減らす。216次元特徴は±1セルのshift-tolerant比較を使用。旧特徴は混在させず新しいlocalStorageキーへ分離。
**再発防止:** 境界推定を改善する変更は、認識率だけでなく「各cropに1牌だけが入っているか」を実機画像で確認する。合成シームテストだけで採用しない。入力cropが安定している場合は、まず分類特徴を改善し、境界処理を過度に複雑化しない。
**回帰テスト:** Chromiumで同一記号を明るさの違う牌面に描いた2画像と別記号1画像を作り、v38の特徴で「照明差のある同一記号」の距離が「別記号」より小さくなることを確認。既存の固定枠撮影・14分割・学習保存・対局/採点フローもCI成功。
**確度:** v37のcrop回帰はユーザー実機スクリーンショットで確認。v38分類の実牌改善量はiPhone確認待ち。

## M057: v38の自動候補8枚のうち4枚が誤認識で、候補数を増やすほど修正負担も増えた
**時期:** M7 v38→v39
**症状:** 14枚を並び替えた実機テストで8/14枚を自動候補化したが、ユーザー確認では正解4枚・誤り4枚。候補のprecisionは50%で、未認識「?」より誤った自動入力の方が確認負担を増やした。
**根本原因:** v38の最近傍テンプレート判定は絶対距離0.30以内かつ2位との差0.012以上で自動採用しており、1〜数枚の学習テンプレートしかない段階としては受理条件が緩かった。特徴量そのものにも改善余地は残るため、4件すべての誤認識を閾値だけが原因と断定はしないが、「曖昧でも自動確定する」判定ロジックはコード上の確定問題。
**修正と次機能:** v39では「誤候補を出さない」precision優先へ変更。最良候補の絶対距離、2位との差、1位/2位距離比をすべて満たす高信頼候補だけ自動入力し、それ以外は「?」のままにする。同時に、?や修正対象をタップした牌選択画面へ上位3候補をショートカット表示し、保守的に自動入力を減らしても手修正のタップ数が増えすぎないようにする。既存v38学習ライブラリはそのまま利用する。
**再発防止:** 認識性能は「何枚候補が出たか」だけで評価せず、候補precision（正解候補/自動候補）を必ず記録する。誤候補が多い段階ではrecallよりprecisionを優先し、曖昧な牌は未確定として人に返す。
**回帰テスト:** Chromiumで明確な1位候補は採用、1位/2位が近い曖昧候補と絶対距離が遠い候補は棄却することを確認。結果画面の牌をタップすると上位3候補のショートカットが表示されること、初回学習保存・固定枠撮影・通常対局/採点フローも通ることを確認。
**確度:** 実機で8候補中4誤りは確定。受理条件が緩いことはコード上確定。特徴量自体の誤り寄与は今後の実機結果で継続評価。

## M058: 学習追加後に高信頼候補のprecisionとTop3 recallが悪化し、連続入力の近い候補も次牌へ更新されなかった
**時期:** M7 v39→v40
**症状:** v39で別順序の14枚を再学習した後、次の実機テストは高信頼候補6枚中2枚正解・4枚誤り（precision 33.3%）。修正が必要な12枚のうち上位3候補に正解が入ったのは4枚（33.3%）。さらに「近い候補」をタップすると連続入力は次の牌へ進むのに、候補欄が前の牌の3候補のまま残り、一度pickerを閉じないと次牌候補を確認できなかった。
**根本原因:** 認識側は各ラベルの全テンプレートから最短距離1件だけで順位付けしていたため、撮影ごとに増えた1枚のノイズテンプレートが他ラベルを誤って引き寄せられる。学習側も同一撮影内の同牌複数枚を個別テンプレートとして保存しており、1撮影の偏りが最大4枠を占有し得た。UI側はv39候補欄をpickerを最初に開いた牌に対して一度だけ生成し、M8 v3.1の連続入力がcurrent indexを進めても再生成していなかった。
**修正:** v40ではラベルごとの複数テンプレートから成分中央値のrobust prototypeを作り、prototype距離72%＋最近傍距離28%で順位付けする。単発ノイズだけが最短になっても自動候補化しにくくする。確定学習時は同じラベルの複数牌を撮影単位で平均し、1ラベルにつき1 prototypeだけ保存する。既存学習ライブラリは維持しながら今後の学習で徐々に安定化させる。連続入力側はcurrent変更イベントを発行し、候補UIはそのたびに現在牌のTop3へ差し替える。
**再発防止:** 学習データ数を増やせば精度が単調に上がると仮定しない。precision/Top3 recallを学習前後で比較する。同一撮影の重複牌でテンプレート枠を埋めない。連続入力の自動遷移を追加する場合、補助UIもcurrent indexと同期する回帰テストを持つ。
**回帰テスト:** Chromiumで単発の異常に近いテンプレートがある場合でもrobust rankingが複数支持の正しいラベルを1位にすること、近い候補1枚目を選ぶとcurrentが2枚目へ進みTop3欄も2枚目用へ即時更新されること、撮影→14枚学習保存→通常対局/採点フローを確認。CI成功。
**確度:** 実機の6候補中4誤り・Top3 4/12・候補UI未更新は確定。最近傍1件依存と同一撮影複数テンプレート保存、UI非同期はコード上確定。v40の実牌精度改善はiPhone確認待ち。
